How this system works

A picture of the autonomy-system in plain language. It is rebuilt from the rulebook itself every time anything lands, so it cannot drift away from what the system actually does.

Reading order: who is on the team → what one paste sets off → what every change has to survive → how the briefings keep themselves current → where things stand today.

  • Lane 1 — Routine (the cheap default)
  • Lane 2 — Plan-touch (novel work)
  • Lane 3 — AUTOPILOT (one paste, hands off)
  • Lane 4 — System surgery (rare, expensive, worth it)

Panel 3

The gauntlet every change walks — six checkpoints, in order

  • 1
    The critique ladder
    A ROUTINE change takes 1 inspection pass. A SIGNIFICANT one takes 3, in a fixed order: Defects, False-green, Final adversarial. On significant work an empty critique or an “LGTM” is a FAILED pass, not a cheap win.
  • 2
    The machine validators
    26 self-tests must pass, and the whole-repo check must come back clean, before anything is allowed to land. Those two run again automatically on the server after the push — but only those two. The extra pre-landing step that catches a DELETED briefing runs on the builder’s machine only, so it is discipline, not a server guarantee.
  • 3
    A named landing route
    Three routes exist and the run says which one it used:
    • Tier 1 — Session-attached repo (best; the only unattended tier)
    • Tier 2 — Local-shell landing (default day-to-day)
    • Tier 3 — One-click fallback
  • 4
    The post-landing read-back
    Someone reads the actual words of the mirrored file to confirm the change arrived. A newer timestamp is not evidence — a broken sync can update the clock and keep the old text. Read the timing honestly: the gate is allowed to DEFER that read to the next run, so the gap between landing and confirmation can be one run wide, and a next run that never happens never discovers a broken sync. The deferral is not a waiver: the next run MUST read the mirror and write down what it found, and a gate may refuse to defer at all whenever a bad sync would be expensive to find late. If you want it checked immediately, say so — that instruction is always available to you.
  • 5
    The gate
    The architect rules RATIFY, FIX or BLOCK and can overturn any decision the crew made.
  • 6
    The permanent record
    Every pass, every dispatch and every ruling is written to the run journal, which held 83 records when this page was built and only ever grows. Claims that cannot point at a record do not count.

Panel 4

The self-briefing loop — no briefing is allowed to go quietly out of date

Every change to the documents or the tools rebuilds all four briefings below, in the same commit as the change. Nobody has to remember to brief anyone.

docs/BRIEF-PACK.md
the operating brief a crew self-briefs from before it touches anything
for the Opus build crews
docs/GROK-CONTEXT.txt
the snapshot pasted at the top of every critique prompt
for Grok, the outside inspector
AGENTS.md
the standing briefing an agent reads when it opens the repo
for Cursor and other outside agents
docs/SYSTEM-MAP.html
this page
for you, the Owner
The enforcement, not the intention: if a briefing is out of date the run FAILS the validator and names the files that moved. That is what stops a briefing from rotting in place. Two limits stated plainly rather than glossed: a fresh briefing proves the sources have not moved since it was built — not that it summarises them well; and DELETING a briefing outright makes the freshness check skip rather than fail, so deletion is the one way a briefing can go quiet without a red light. The detector for that is --check on both generators, which runs on the builder’s machine as a separate pre-landing step and is not repeated by the server.

Precedence is fixed and one-directional: the canonical document always wins. These four files are a fast path to the current state, never an authority, and nothing may be closed, ratified or landed on one of them alone.

Generated file — do not hand-edit. tools/gen_map.py writes this page from 15 canonical documents, listed with their fingerprints in the manifest comment at the end of this file. Hand edits are overwritten at the next landing, and the SELF-DIGEST in that manifest is what makes such an edit detectable. It rebuilds itself at every landing: any change under docs/ or tools/ must regenerate it in the same commit, and tools/validate_journal.py --all fails a run that leaves it stale.

Canonical documents win. This page is a picture of the rules, never the rules themselves. On any disagreement between this page and a canonical document, the document is right and this page is stale. Nothing may be closed, ratified or landed on the strength of this file.

What the freshness check does and does not prove. It proves the source documents have not changed since this page was built. It does not prove the page describes them well. Every lay claim above is additionally anchored to an exact phrase that must still be present in a named document, and generation fails loudly if one goes missing — but a phrase can survive inside a paragraph whose meaning was reversed, and no check here would notice that. One figure sits outside the manifest on purpose: the journal record count, because the journal is append-only evidence that grows after this page is built, so that number is a floor read at build time rather than a live reading. The last landed commit (the current baton records no pushed SHA (STAGED)) is read from the run baton, not from git.
